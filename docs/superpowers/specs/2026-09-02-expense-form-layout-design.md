# 支出表單重排：三張卡、固定送出列、抽出地點欄位

日期：2026-09-02

## 目標

`ExpenseFormPage.vue` 是全專案最大的檔案（1104 行：script 594 / template 329 /
style 176），也是使用者最高頻的操作。它有一個明確的問題：

**13 個欄位平鋪在同一張卡裡，而其中只有兩個是真的必填。**

`canSubmit` 只檢查三件事——名稱有字、金額解析得出來、至少有一個分攤成員，
而分攤成員預設是全選。其餘九個欄位全都有能用的預設值：分類是 `food`、
幣別是 `TWD`、日期是今天、誰先付是自己、分攤方式是均分。

所以記一筆拉麵錢只要打兩個欄位，卻要捲過十一個區塊才按得到最底下的送出鈕。
這跟前兩輪在解的是同一個病——每個東西的視覺重量都一樣，所以真正重要的那兩個
沒有重量——只是在表單上代價更高，因為記帳常常是在餐廳裡站著單手做的。

## 範圍

**要做的**

- 13 個欄位重新分成三張卡，依「你會不會動它」而不是依主題
- 送出鈕固定在畫面底部
- 「分攤方式」從 `.tabs` 換成 `.seg`
- ~~地點地圖 180px → 120px~~（實作後推翻，見 §3.2）
- 匯率區塊從三塊壓成兩行
- 刪掉 `queuedNotice` 的死程式碼
- 把地點那一整塊抽成 `PlaceField.vue`，跟 `flutter_app/lib/ui/place_field.dart` 對齊
- 把 `currentPlace()` 抽成純函式並補測試

**明確不做的**

- **不做漸進揭露。** 所有欄位一律展開，新增與編輯行為一致。理由：編輯時你是
  為了改某一個特定欄位而來的，把欄位藏起來會讓你多點兩下才找得到。
- **不重構 `placeService.ts`。** Flutter 的 `domain/place_search.dart` 已經把
  Places API 回應的解析從網路那半拆出來並測了（`parseSuggestions`、
  `parsePlaceDetails`、`placeErrorHint`），網頁版仍然混在一起而且沒有測試。
  那是服務層的重構，不是這一頁的版面工作。**記錄，不做。**
- **不改任何金額計算、分攤邏輯或送出流程。**
- **不動 `flutter_app/`。**
- **不修「選外幣時匯率欄位憑空出現」造成的版面位移。** 那是使用者剛換了幣別
  造成的，欄位就出現在他正在看的地方——讀起來是「系統回應了我」，不是「畫面亂跳」。

## 一、三張卡

依「你會不會動它」分，不是依主題分。

### 卡 1（主卡，沒有小標）

分類 chips · 支出名稱（含語音）· 金額 ＋ 幣別（同一列）· 匯率（跨幣別時）

它是主角，不需要一個標題來宣告自己是主角。兩個必填欄位都在這裡，
所以打完就能按送出。

### 卡 2「這趟的細節」

日期 ＋ 時間（同一列）· 地點 · 收據 · 備註

### 卡 3「怎麼分」

誰先付 · 分攤方式 · 分攤成員／每人金額

### 三個刻意的安排

**匯率留在卡 1。** 它是「多少錢」的一部分，搬去別張卡會讓人找不到。

**分類 chips 留在最上面。** 它不是必填（有預設值），但它是六選一的 chips、
高度只有一行多、而且是最常改的。放在名稱上面，手指從分類滑到名稱是連續動作。

**「誰先付」放卡 3 不放卡 1。** 它預設是自己，而且概念上屬於「這筆錢怎麼算」，
跟分攤方式、分攤成員是同一組。放卡 1 會把主卡撐大，換不到相應的價值。

### 為什麼不依主題分

依主題分（「這筆是什麼／多少錢／什麼時候在哪／怎麼分」）邏輯比較自明，
但要四張卡——**卡片的 padding 與間距是有成本的，總高度會比現在更長**，
而縮短捲動距離正是這次的目標。而且那樣分會把「金額」推到第二張卡，
那是兩個必填之一。

## 二、固定送出列

### 2.1 只有送出鈕進固定列

固定列包含：**送出鈕**，以及**有錯誤時的錯誤訊息**（錯誤在上、按鈕在下）。

錯誤必須跟著進去。送出失敗時 `error` 會被設值，但如果它印在捲動流的底部而
使用者停在上面，他會按了送出、什麼都沒發生、也不知道為什麼。

頁面底部要補足夠的 padding，否則最後一個欄位會被固定列蓋住。

**用 `position: sticky; bottom: 0` 而不是 `position: fixed`。** 這一頁到處是
文字輸入框，而 iOS Safari 的虛擬鍵盤跳出來時，`fixed` 元素的行為是出了名的
不可靠——它可能被鍵盤蓋住、也可能浮在鍵盤上方擋住正在打字的欄位。
`sticky` 黏在捲動容器內，跟著內容走，鍵盤怎麼動都不會錯位。

這跟 `styles.css` 裡那幾條 iOS Safari 的原生控制項修正是同一類問題：
桌面瀏覽器上兩種寫法看起來一樣，手機上只有一種能用。

### 2.2 刪除與取消留在捲動流裡

**這條不能妥協。** `93be088`（*Stop putting the destructive button under the thumb*）
動的正是這個檔案，理由寫得很清楚：手機上系統對話框「OK 落在哪不是我們能決定的，
而它傾向落在拇指下」。

固定在螢幕底部的那一條就是拇指的定位點。把不可逆的「刪除支出」放進去，
等於把這個檔案自己修掉的問題原樣放回來。

附加好處：使用者可能永遠不會捲到底，所以**刪除需要刻意捲下去才找得到**——
那正是它應得的摩擦。

取消也留在下面：它是「放棄剛打的東西」，而返回鍵本來就能離開，
不需要在拇指位置常駐一顆。

## 三、一併處理的四件事

### 3.1 「分攤方式」換掉 `.tabs`

它現在用的是任務頁最上層那個導覽元件（`.tabs.two`，選中態是墨黑實心）。
那是頁面層級的視覺重量，用在表單裡的一個二選一上太搶。

換成 `2026-09-02-task-page-settlement-summary` 那輪做的 `.seg`（白底選中）——
它就是為次層級切換做的。

### 3.2 地圖維持 180px（原訂 120px，實作後推翻）

原本的理由是：它的用途只是「確認選對地方了」，不是拿來看的，120px 還看得到
圖釘與周邊但少推 60px。

**做出來之後看，120px 太扁。** 圖釘周邊能認出「是不是這條街」的資訊少一截，
而省下的 60px 相對於三張卡與固定送出列省下的捲動距離佔比很小 ——
收益換不到代價。維持 180px。

### 3.3 匯率區塊從三塊壓成兩行

現在是輸入框 ＋ 換算後金額 ＋ 格式錯誤三個區塊。換算後金額壓成輸入框下面
一行灰字（`≈ TWD 672`），格式錯誤維持獨立一行（那是錯誤，該有重量）。

### 3.4 刪掉 `queuedNotice` 的死程式碼

`submit()` 在成功時是：

```ts
if (outcome === "queued") queuedNotice.value = true;
await router.push(`/tasks/${taskId}`);
```

設完旗標**立刻導走**，元件跟著卸載——那個 `<p v-if="queuedNotice">` 沒有機會
渲染。所以離線存檔時使用者收不到「已存在這台裝置上，連上網會自動同步」這句話，
而那正是最需要安撫的時刻。

**刪掉 `queuedNotice` 的 `ref` 與那段 template。**

**但要記下原意**：離線排隊時應該要告訴使用者。這個提示是有人想過的，只是實作
壞了——刪掉之後如果沒有記錄，下一個人會以為從來沒想過這件事。修法不只一種
（延後導航、在任務頁顯示、改用全域提示），每一種的影響範圍都超出這次改版。

## 四、`PlaceField.vue`

地點那一整塊——搜尋、建議清單、定位、位置偏好、地圖——自成一個完整的東西，
而 `flutter_app/lib/ui/place_field.dart` 早就抽出來了，只有網頁版沒抽。

### 4.1 介面

Flutter 是 `initial` + `onChanged`；Vue 的等價寫法是 `v-model`：

```ts
defineProps<{ taskId: string }>();
const place = defineModel<ExpensePlace | null>();
```

`taskId` 是位置偏好（`recallPlaceBias`）需要的。

### 4.2 搬進去的東西

九個 `ref`：`placeQuery`、`selectedPlace`、`suggestions`、`placeLoading`、
`locating`、`placeError`、`placeBias`、`myLocation`，以及 debounce timer 與
session token。

兩個 computed：`placeMarkers`、`canLocate`。

三個函式：搜尋（含 debounce）、定位、清除。

母元件因此少掉約三分之一的狀態。

### 4.3 兩條要原文寫進註解的行為契約

從 Flutter 版繼承，因為兩邊必須是同一個東西：

**定位抓到的座標不會存進支出。** 那顆鍵只回答「我在哪」，不去猜你人在哪家店。
它只做兩件事：換掉搜尋的位置偏好，以及在還沒選地點時讓地圖有東西可以顯示。

**一改字就作廢選過的建議。** 改過的名字已經不是那個地點了，座標必須跟著丟掉。

## 五、可測的部分

跟前兩輪一樣，測試套件看不到版面。但第二條契約現在是 `currentPlace()`，
藏在元件裡、是純函式、而且**寫錯的畫面看起來完全正常**——會存進一個名字
對不上座標的地點。

抽成 `src/utils/placeSearch.ts`（名字跟 Flutter 的 `domain/place_search.dart`
對齊）：

```ts
import type { ExpensePlace } from "@/types/expense";

/**
 * 這一格現在代表哪個地點。
 *
 * 選過建議就是完整的那一份（含座標），只打了名字就是只有 name 的那一份，
 * 空的就是 null。
 */
export function currentPlace(query: string, selected: ExpensePlace | null): ExpensePlace | null;

/** 太短就不要查 —— 每打一個字打一次 API 太浪費，而一兩個字也搜不出東西。 */
export function shouldSearchPlace(query: string): boolean;
```

### 5.1 要補的測試

`tests/placeSearch.test.ts`（新增）：

- `currentPlace` 空字串、只有空白，都回 `null`
- `currentPlace` 只打了名字沒選建議，回一個 `lat`/`lng`/`placeId` 都是 `null` 的地點
- `currentPlace` 名字跟選過的建議一致時，回那一份完整的（含座標）
- `currentPlace` **名字被改過之後，座標要丟掉**——這是最重要的一條，
  它防的是「存進一個名字對不上座標的地點」
- `currentPlace` 會 trim，前後空白不影響是否與選過的建議相符
- `shouldSearchPlace` 少於兩個字回 `false`，兩個字以上回 `true`，
  只有空白回 `false`
