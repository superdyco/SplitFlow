# 分帳系統 — 單一版面響應式設計

日期：2026-07-31

## 目標

把 `index.html` 原型從「手機版 ＋ 桌機版兩套畫面」改成**一套畫面**，在手機與桌面瀏覽器都能完整操作，功能完全相同。

這份原型的定位是**設計稿**：正式產品之後會用 React/Vue ＋ Firebase 重寫。因此本文件的交付物是**版面決策**（斷點數字、各斷點下的排列規則），不是可上線的程式碼。原型只需要忠實表現這些決策，好讓正式開發照著做。

## 現況問題

`index.html` 目前有兩棵完全獨立的 markup 樹：

- `isPhone` 分支（第 179–497 行）— 七個畫面全在這裡
- `isDesktop` 分支（第 56–164 行）— **只有「任務內頁」一個畫面**

後果有二。其一，桌機開啟時只看得到一張靜態假畫面，登入、建暱稱、任務列表、建立任務、邀請連結、新增支出這六個流程在桌機上不存在。其二，「任務內頁」被實作了兩次，兩邊的樣式與內容各自漂移，改一處要記得改兩處。

版面切換目前由 JS 負責：`componentDidMount` 掛 resize listener 把視窗寬度寫進 `vw` state，`renderVals()` 再依 `vw` 算出幾十條 style 字串。斷點有三層（900 / 1080 / 1320），其中 1320 是為了原型外框而存在的。

## 決策一：移除原型鷹架

一旦確定「這是一個網頁 app」，以下元素都不該存在於設計稿中：

| 移除項目 | 現況位置 | 理由 |
|---|---|---|
| 裝置切換器（手機版／網頁版／自動） | 第 45–54 行、`setPhone`／`setDesktop`／`setAuto` | 產品裡沒有這顆按鈕，留著會誤導閱讀設計稿的人 |
| 假手機殼與圓角邊框 | `phoneShellStyle`、`phoneInnerStyle` | 網頁 app 不會把自己畫在手機殼裡 |
| 假狀態列（9:41 · 5G · 電池） | 第 170–176 行 | 原生 app 截圖的裝飾 |
| 假 home indicator 橫條 | 第 499–501 行 | 同上 |
| 假瀏覽器 chrome（三圓點＋網址列） | 第 58–65 行 | 網頁 app 不需要畫一個瀏覽器來裝自己 |
| 左側 01–07 畫面導覽列 | 第 26–42 行、`nav`／`navItems` | 見下方說明 |
| `device`、`vw` state 與 resize listener | 第 542、551–556 行 | 版面改由 CSS 決定，JS 不再需要知道視窗寬度 |
| 衍生變數 `bare`、`wide`、`desktopOn` | 第 589–591 行 | 隨上述一併消失 |

導覽列可以移除，是因為七個畫面靠正常操作全都到得了：登入 →（Google／FB 登入）→ 建暱稱 →（建立帳號）→ 任務列表 →（建立分帳任務）→ 建立任務 →（建立並取得邀請連結）→ 邀請連結 →（進入任務）→ 任務內頁 →（新增支出）→ 新增支出。每個內頁都有返回鍵。跳頁捷徑不但多餘，還會讓人誤以為它是產品的一部分。

## 決策二：單一斷點 960px

只設一個斷點。

數字來源：支出列表舒適閱讀寬度約 560px ＋ 結算面板 340px ＋ 欄距與內距約 60px ＝ 960px。低於此寬度硬排兩欄，兩邊都會擠。

現行的 900 / 1080 / 1320 三層斷點全部作廢——它們是為了原型外框而生的，外框拆掉後失去意義。

## 決策三：畫面分兩類，多數不需要斷點

**A 類 — 單一焦點畫面**：登入、建暱稱、建立任務、邀請連結、新增支出。

內容本來就只有一欄。統一套用 `width:100%; max-width:480px; margin:0 auto`，手機滿版加左右內距，桌機自動收成置中卡片。**這類完全不使用媒體查詢**，一條規則同時服務兩端。

**B 類 — 資料密集畫面**：任務列表、任務內頁。

任務列表用 `grid-template-columns: repeat(auto-fill, minmax(320px, 1fr))`，容器 `max-width:1200px` 置中。手機自然單欄，桌機自動排成兩到三欄，**同樣不需要斷點**。

任務內頁是唯一真正用到 960px 斷點的畫面，規則見決策四。

## 決策四：任務內頁的面板重排

支出、成員、結算不是三個「頁籤」，而是三個 **panel**。頁籤只是空間不足時的降級形式。三者在 markup 中各出現一次，排列方式隨寬度變化：

| | < 960px | ≥ 960px |
|---|---|---|
| 版面 | 單欄 | 兩欄 grid：左 `1fr` ／ 右 `340px` |
| 支出 panel | 頁籤之一 | 左欄，依頁籤顯示 |
| 成員 panel | 頁籤之一 | 左欄，依頁籤顯示 |
| 結算 panel | 頁籤之一 | **右欄常駐** |
| 頁籤列 | `[支出] [成員] [結算]` | `[支出] [成員]`，第三顆隱藏 |

結算是唯一值得常駐第二欄的內容，因為記帳當下使用者會反覆查看目前誰欠誰。成員管理（設為管理者、邀請成員）屬於低頻設定操作，留在頁籤即可。這個安排讓寬螢幕不需要新增任何元件，頁籤列只是少一顆。

### 頁籤狀態與寬度的交互

`tab` state 仍由 JS 持有（`"expenses"｜"members"｜"settle"`），但 JS 不再知道視窗寬度，因此無法在變寬時自動修正 `tab`。若使用者在窄螢幕選了「結算」後放大視窗，左欄兩個 panel 都會被隱藏而留白。

解法不需要 JS：把 `tab` 以 `data-tab` 屬性寫在任務內頁容器上，由 CSS 在寬螢幕下讓「結算」退化為「支出」：

```css
@media (min-width: 960px) {
  [data-tab="settle"] .panel-expenses { display: block; }
  [data-tab="settle"] .tab-expenses  { /* 同時呈現為選中狀態 */ }
}
```

亦即寬螢幕下 `tab === "settle"` 時，左欄顯示支出，且「支出」頁籤按鈕呈現選中樣式，使畫面與頁籤狀態一致。`tab` state 本身不變動。

## 決策五：跨畫面規則

**共用 header** — 登入後的五個畫面（任務列表、建立任務、邀請連結、任務內頁、新增支出）共用同一條 header，同一棵 markup。窄螢幕顯示「返回鍵＋標題＋動作鍵」；寬螢幕在同一條上追加 logo 與使用者頭像，靠 CSS 顯隱，不另開分支。登入與建暱稱兩個畫面沒有 header，維持現行的全版式版面。

**主要按鈕** — 窄螢幕滿版吸附底部；寬螢幕改為靠右對齊、寬度自適應。滿版 56px 高的橘色按鈕在 1400px 寬的螢幕上會顯得突兀。

## 實作方式

改用 CSS class ＋ `<helmet>` 內的 `<style>`，取代現行「JS 計算 inline style 字串」的寫法。已驗證 dc-runtime 支援：

- `support.js:436` — `class` 屬性會轉成 React 的 `className`
- `support.js:1475-1490` — `<helmet>` 內的 `<style>` 會原封不動建成真的 `<style>` 元素塞進 `document.head`，無 scoping，因此 `@media` 完全可用

保留 inline style 的時機：值真的來自資料而非版面的地方，例如成員頭像顏色 `AV[name]`、收支正負色 `#0E9F6E`／`#D63939`、選中狀態的樣式。版面相關的樣式一律進 CSS。

現行的 `style-hover` 屬性可改用真正的 `:hover` 偽類。

### state 變更

移除 `device`、`vw` 兩個欄位，以及 `componentDidMount`／`componentWillUnmount`。其餘欄位（`screen`、`tab`、`nickname`、`taskName`、`taskCurrency`、`copied`、`settled`、`admins`、`formCurrency`、`formAmount`、`formTitle`、`placeIdx`、`formCat`、`payer`、`split`）維持不變。

商業邏輯 `totals()` 與 `transfers()` 不動。順帶修掉 `renderVals()` 中 `this.transfers(net)` 被呼叫兩次的問題（一次取清單、一次取長度），改存區域變數。

## 驗收標準

在以下寬度手動檢查，每個寬度都要能走完完整流程（登入 → 建暱稱 → 任務列表 → 建立任務 → 邀請連結 → 任務內頁三個面板 → 新增支出 → 儲存返回）：

- **390px**（手機直立）— 單欄，無橫向捲動，主要按鈕吸附底部
- **768px**（平板）— 仍為單欄，A 類畫面已收成置中卡片
- **1024px**（小筆電）— 任務內頁兩欄，結算常駐右側
- **1440px**（桌機）— 內容置中不無限延展，任務列表排成多欄

另需確認：在 390px 選「結算」頁籤後放大到 1024px，左欄顯示支出而非留白。

## 範圍外

以下明確不做：

- 不接 Firebase、不接真實登入、不接 Google Maps。示範資料（`RATES`、`EXPENSES`、`PLACES`、四位成員）維持寫死。
- 「新增支出」在桌機不做成 modal 對話框，沿用 A 類的置中卡片規則。modal 需要額外的元件機制，且不影響版面決策的表達。
- 不新增畫面、不新增功能。本次只改版面。
- 不做深色模式。
