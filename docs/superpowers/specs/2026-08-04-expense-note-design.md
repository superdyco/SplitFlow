# 支出備註

日期：2026-08-04

## 目標

支出可以加一段自由文字，記下「這筆為什麼要這樣記」——「含小費」「阿明先付現金」
「發票在小美那」這類對帳時會需要、但塞不進支出名稱的資訊。

## 範圍

**要做的**

- 支出新增與編輯頁可填備註，上限 500 字
- 支出列表顯示備註，一行截斷
- Firestore 規則驗證型別與長度

**明確不做的**

- **不進公開旅費報告。** 那份規格明文不放支出名稱；備註比支出名稱更私密
  （「阿明先付現金」直接點名），公開出去等於替別人決定。
- **「再記一筆」不帶備註。** 見下面的理由。
- **不做搜尋或篩選。** 備註是給人看的，不是索引欄位。

## 資料模型

```ts
/** 這筆支出的補充說明。空字串代表沒有備註。 */
note: string;
```

加在 `Expense` 與 `ExpenseInput` 上。

**用空字串而不是 `string | null`**：`place` 與 `receipt` 是物件，「沒有」只能用 null
表達；純字串的空值就是空字串，而且結算快照的 `note` 已經是這個形狀，跟著走比較一致。
少一個 null 檢查，模板也不用寫 `note ?? ""`。

舊支出沒有這個欄位，`normalizeExpense` 補 `?? ""`。

## 安全規則

在 `validReceipt()` 旁邊加，並掛進 `validExpenseShape()`：

```
// 備註是選填。用 .get() 是因為這個功能之前建立的舊支出沒有這個欄位。
function validNote() {
  let note = request.resource.data.get("note", "");
  return note is string && note.size() <= 500;
}
```

## 介面

### 表單

放在收據之後、「誰先付」之前 —— 地點、收據、備註都是「這筆消費的補充說明」，
擺在一起讀起來是一組。

用 `<textarea>` 而不是單行 `<input>`。專案目前沒有任何 textarea（結算的備註是單行），
所以要多加幾行 CSS。理由是 500 字塞在單行輸入框裡要左右捲才看得完，寫得下但讀不回來。
結算備註用單行是因為那裡通常很短（「回國當天結算」），支出備註的範圍開放得多。

`maxlength="500"` 直接擋在輸入端，比照 `title` 的 `maxlength="60"` ——
這樣**根本產不出不合法的值**，不需要再多一個錯誤訊息。

### 列表

`ExpenseRow` 加一行 `📝 {{ note }}`，跟 📍 地點同樣的 `text-overflow: ellipsis`
一行截斷。只在有備註時出現，沒備註的支出完全不受影響。

**注意 `ExpenseRow` 的 template 有兩個幾乎相同的分支**（`canManage` 與非 `canManage`，
因為 stretched link 的結構不同）。備註要加在**兩邊**，只改一邊的話沒有管理權的成員
就看不到備註。這個坑在加 📎 收據標示時已經踩過一次。

**為什麼要顯示在列表**：備註的用途是對帳當下就想看到的資訊。要點進去才看得到的話，
等於每筆都要點一次，備註就失去意義了。

## 「再記一筆」不帶備註

`repeatFieldsOf` 目前帶走 title、category、currency、paidBy、splitMode、splits、place
—— 那些是「這種消費固定長這樣」。

備註是這一次的狀況（「阿明先付現金」「含小費」），下次不一定成立，跟金額與日期同一類。
帶過去的話使用者很容易忘記刪掉，留下一句對新支出不成立的說明，比沒有備註更糟。

## 驗收標準

1. 新增支出可填備註，存得起來，重新載入還在。
2. 編輯支出看得到既有備註，改得動。
3. 支出列表在有備註時顯示 `📝`，過長時截斷成一行、不會撐破版面。
4. 「再記一筆」帶出的表單，備註是空的。
5. 這個功能之前建立的舊支出照樣讀得到、編輯得動。
6. `npm test` 全綠。
